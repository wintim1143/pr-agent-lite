### 根因：不是 IP 封锁，是 **SNI 阻断**

| 探测 | 结果 |
|---|---|
| tcp `github.com:443` / `:22` / `ssh.github.com:443` | **全部 OPEN** |
| `https://api.github.com` | **200** ✅ |
| `https://raw.githubusercontent.com` | 301（可达） |
| `https://codeload.github.com` | 301（可达） |
| `https://github.com/…git/info/refs`（HTTPS git 协议） | **超时 FAIL** |
| `ssh -T git@github.com` | **`Permission denied (publickey)`** ← 协议层通，仅缺 key |
| `ssh -T -p 443 git@ssh.github.com` | 同上 |
| 直连 github.com git（屏蔽全局配置） | 超时 |
| gh-proxy.com / ghproxy.net 首页 | 200，**但其 git 端点全部不通** |
| ghfast.top git / gitclone.com git | 403 / 502 |
| codeload tarball 下载 | 超时 |

**结论**：TCP 全通 ⇒ 不是 IP 封锁；`github.com` 与 `codeload` 的 **HTTPS 被 SNI 阻断**，而同域名族的 `api.github.com`、`raw.githubusercontent.com` 未被阻断；**SSH（无 SNI 概念）完全可用**。第三方镜像对 git 协议全部失效，不要指望它们。

## 补充核实：本机 vs 服务器（用户提出「可能是代理问题」）

用户提示「我电脑已配置 ssh key，可能是代理的问题」→ **用户的直觉对了一半，但适用对象是本机，不是服务器。**

### 本机（mac，实测）

`~/.ssh/config` 对 github 的配置**不是默认路径**：

```
Host github.com
    HostName ssh.github.com        ← 走 443，不是 22
    User git
    Port 443
    ProxyCommand nc -X 5 -x 127.0.0.1:7890 %h %p    ← SOCKS5 本地代理
```

- `ssh -T git@github.com` → **`Hi wintim1143! You've successfully authenticated`** ✅
- 本机 key：`id_rsa`（2024-11，GitHub 用）、`id_ed25519_tencent`（2026-06，**登录服务器用，与 GitHub 无关**）

⇒ 本机是「**代理 + key 两者同时具备**」才通。代理端口 7890（典型 Clash/Mihomo）。

### 服务器（实测，逐项查过）

| 查项 | 结果 |
|---|---|
| `~/.ssh/` | 只有 `authorized_keys`（他人 ssh 进来用）+ **我刚生成的** `id_ed25519`；**无任何用户预置 key** |
| ssh-agent | **未运行**（`SSH_AUTH_SOCK` 为空） |
| 代理环境变量 | 只有 `GOPROXY`（Go 镜像，**与网络代理无关**） |
| `/etc/environment` | 只有 `GOPROXY` |
| `/etc/profile.d/` | 只有 `go_conf.sh` |
| 系统 `/etc/ssh/ssh_config` | 无 `ProxyCommand` |

⇒ **服务器上既不存在代理，也不存在用户 key。**

### 关键判据：`Permission denied (publickey)` 不是网络问题

该响应由 **GitHub 在 SSH 握手与密钥协商全部完成后**返回。若是代理/网络故障，表现应为超时或 `Connection reset`。
⇒ **服务器 SSH 到 GitHub 的链路完整可用、不需要代理，只缺一个 GitHub 认识的 key。**

### 为什么不能直接复用本机 key

复用必须把**私钥**复制到服务器 —— 代价是服务器上任何进程（含被编码 agent 写入的代码）都能拿到该 GitHub 账号的完整钥匙。**服务器自建独立 key 是标准做法**（可单独撤销、可降级为单仓库 deploy key）。已生成的就是这把。

### 为什么用 bundle 而不是 rsync 整目录

服务器上的常驻副本**就是编码 agent 的工作区**（会建分支、改文件）。整目录 rsync 带 `--delete` 会抹掉工作区改动；**bundle 只更新 refs 与对象、不碰工作树** ⇒ 语义正确。
代价：bundle 是全量快照（本项目 332 KB 量级可忽略）；仓库变大后可用范围语法做增量（**未实测**）。

## 11:50 — `~/code` 项目级 Claude 配置 + 权限实验（含一次被污染的对照）

用户要求：在 `~/code` 下加**项目级**配置，**默认放开所有权限**。

### 一手来源（官方文档，v2.1.276 对应行为）

| 事实 | 出处 |
|---|---|
| `permissions.defaultMode` 的 `auto` / `bypassPermissions` **从项目级 / 本地级设置不生效**，会话回落到 Manual | `code.claude.com/docs/en/permission-modes` 原文：*"If you set `bypassPermissions` in those two files, it doesn't take effect either, and the session starts in Manual mode."*（v2.1.257 前才允许从任何文件生效） |
| 项目级设置**除 `auto` 与 `bypassPermissions` 外的值都生效**（如 `acceptEdits`） | 同上 |
| 权限规则语法：**裸工具名 ≡ `Tool(*)`**（`Bash` 即放行全部 Bash 命令） | `…/docs/en/permissions` 规则语法 |
| `allow` **不接受**未锚定通配（`"*"`、`"mcp__*"`）—— 会被跳过并给启动警告 | 同上 |
| 优先级铁律：**deny > ask > allow**，且跨级 deny 不可被 allow 覆盖 | 同上 |

### 已落地（项目级，实测生效）

`~/code/.claude/settings.json`（仓库内副本 `scripts/claude-project-settings.json`）：

**实测**：不带任何命令行参数，Bash 写文件 + Write 建文件**全部通过、无提示**；启动无「非法工具名」警告。⇒ **项目级能达到「日常无提示」，但达不到 `bypassPermissions` 那条硬放行。**

### 🔴 对照实验先被污染、后做干净（教训）

第一次对照在 `/tmp` 下建项目 → 报「输出重定向被沙箱阻止，只能写会话允许的工作目录」。我差点把它当成「bypass 未生效」的证据 —— **其实那是沙箱（文件系统）限制，不是权限模式**。

根因：`/home/ubuntu/code` 的 `~/.claude.json` 里有 `hasTrustDialogAccepted: true`，`/tmp` 下的目录**未信任** ⇒ 沙箱更严。两个变量混在一起，对照无效。

**干净对照**（在已信任的 `~/code` 内做，临时换配置再恢复）：项目级只放 `{"permissions":{"defaultMode":"bypassPermissions"}}` → `Write` 调用**被权限拒绝** ⇒ **与官方文档一致，项目级 bypass 确实不生效**。

**教训**：做对照实验前先确认「只有一个变量在变」。「沙箱拒绝」与「权限拒绝」是两条不同的轴，报错措辞必须读准。
