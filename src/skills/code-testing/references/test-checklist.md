# Test Checklist — 测试闸门核对清单

`code-testing` skill 「详见」的参照明细。改动必须过此清单才能放行进入 `code-review`。

## A. 跑测试（红线）

- [ ] `npm test`（jest）全绿。任一用例失败 → 标红打回，**不可放行**。
- [ ] 新增行为必须配测试，尤其是：
  - 跨步骤上下文传递（顺序执行器的 `inputSchema` / `outputSchema` 衔接）；
  - 「步骤输出不符合 `outputSchema` 就判该步失败」这条 fail-closed 语义 —— 改了执行器必须重验；
  - `usage` 形状收敛（`log-store.toV3Usage` / `normalizeUsage`）—— 它的失败形态是**静默**的。

## B. 测试写法规约（本项目踩过的坑）

- [ ] **测试不得污染生产证据**：日志落盘路径由 `jest.setup.ts` 重定向到临时目录。
      这个文件**必须保留** —— 日志是「程序真的做了什么」的真相源，混入测试事件后判据就废了。
- [ ] **测试不得污染生产状态库**：用环境变量把库路径指向临时文件，且必须在 **import 状态库模块之前**设置
      （该模块加载即读环境变量定路径）。不用环境变量就会在仓库根留下一个库文件。
- [ ] 触碰状态库（LibSQL / SQLite 族）的测试，**必须在 `afterAll` 先 `await close()` 再删文件**：
  - Windows 下这类驱动持有 `-wal` / `-shm` 文件锁，紧跟的 `rmSync` 会报 `EBUSY: resource busy or locked`；
  - 未释放会**每次跑泄漏一个临时库文件**；
  - 若两个实例各自建连接，需逐个 `close()`（未必复用同一连接）；
  - 删文件用「遇 EBUSY 退避重试」封装，兼容驱动异步释放锁。
- [ ] 不写依赖外部网络 / 凭据的测试（本环境未配置 LLM 凭据、未装平台 CLI）。端到端调用应 mock 或留 TODO 桩。
- [ ] 断言用「**实际执行数**」口径对账：`it.each` 声明一次、按数据组展开成多条，
      而 CI 打印的是执行数 —— 用声明数对账必然对不上。

## C. 回归保护

- [ ] 改动未破坏既有用例（`npm test` 全量跑，不只跑单文件）。
- [ ] 若改了 `tsconfig` / `jest.config.js` / 构建脚本，确认 `npm run build` 仍通过、`npm test` 仍可收集。

## D. 覆盖度建议

- [ ] 边界值、空输入、异常分支有对应用例或显式标注「已知未覆盖」。
- [ ] 关键架构约束（步骤顺序、闸门不通过不继续、`guard` 保持纯函数）有回归测试守护，误删配置即失败。
